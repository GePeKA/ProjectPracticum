# Конвенции

Документ описывает, как устроен репозиторий и как в него попадают изменения.

## Проекты

Solution `Sprosi.sln` лежит в корне.

Проекты .NET лежат в `src/`:

| Проект | Роль |
|---|---|
| `Sprosi.Domain` | Сущности предметной области, без зависимостей |
| `Sprosi.Application` | Сценарии, DTO и интерфейсы репозиториев |
| `Sprosi.Data` | EF Core, контекст базы и реализации репозиториев |
| `Sprosi.Infrastructure` | Внешние механизмы: пароль, JWT |
| `Sprosi.Api` | HTTP и сборка приложения в `Program.cs` |

Каталог проекта совпадает с его именем. Namespace совпадает с именем проекта.

Тесты лежат в `tests/`. Интерфейс лежит в `frontend/` и в solution не входит.

Зависимости направлены внутрь:

- Domain ни на кого не ссылается.
- Application ссылается на Domain.
- Data и Infrastructure ссылаются на Application.
- API ссылается на Application, Data и Infrastructure.

Контроллер вызывает сервис Application. К базе обращаются только репозитории. Контекст EF и регистрация репозиториев живут в Data и подключаются методом `AddData()`.

Имена в коде на английском. Тексты интерфейса, сообщения об ошибках и документация на русском.

Локальная строка подключения к PostgreSQL и ключ JWT для локального запуска лежат в `appsettings.json`.

## Коммиты

Сообщение коммита на английском:

```text
type(scope): summary
```

Тип: `feat`, `fix`, `chore`, `docs`, `test`, `ci`.

Область — слой или часть репозитория: `repo`, `domain`, `application`, `data`, `infrastructure`, `api`, `frontend`.

```text
feat(domain): add question and answer
fix(application): reject an empty title
docs(api): describe registration
chore(repo): add layer projects
ci(repo): build the backend and frontend
```

Автор коммита — владелец репозитория. Соавтор в сообщении не указывается.

## Pull request

Долгоживущие ветки — `main` и `dev`. Напрямую в них не коммитят.

Новая ветка создаётся от актуального `dev`. Имя начинается с `feat/`, `fix/`, `chore/` или `docs/` и дальше идёт короткое английское название через дефис. После вливания ветка остаётся в удалённом репозитории.

Pull request открывается в `dev`. Один запрос — одна законченная тема.

Заголовок pull request в том же формате, что и коммиты, например `feat(domain): add question and answer`. Описание на русском и состоит из трёх частей: что сделано, зачем, как проверить. Тот же каркас лежит в `.github/pull_request_template.md`.

В `dev` изменения вливаются merge-коммитом, чтобы история ветки сохранилась.

В `main` попадает весь `dev`, когда закрыт заметный кусок работы: каркас репозитория, готовое API, интерфейс вместе с инструкцией по запуску.
